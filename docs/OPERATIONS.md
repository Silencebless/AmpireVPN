# Эксплуатация AmpireVPN

## Деплой без простоя (режим масштабирования)

```bash
git pull
./deploy/scripts/rolling-update.sh
```

Скрипт собирает образ, поднимает рядом столько же новых реплик `api`, ждёт `healthy`, затем **по одной** останавливает старые
(`stop_grace_period: 45s` — реплика дорабатывает запросы и фоновые задачи), после чего перезапускает `worker`.
Если новые реплики не стали `healthy`, они удаляются, а старые продолжают работать.

Правила для безопасной раскатки:

* миграции БД применяются при старте первой новой реплики, поэтому должны быть **обратно совместимы** со старым кодом
  (добавление колонок/таблиц с значениями по умолчанию; удаление и переименование — отдельным релизом позже);
* на одиночной установке (`docker-compose.yml`) простой при `up -d --build` неизбежен (десятки секунд) — делайте это ночью.

## Корректная остановка

`docker stop` отправляет SIGTERM; процесс: прекращает принимать запросы → дожидается фоновой обработки вебхуков оплаты (до 20 с) →
доводит итерацию задач воркера (до 15 с) → рассылка сохраняет курсор и продолжится после запуска. Платёж, принятый вебхуком,
не теряется: если процесс всё же оборвётся, его добёрет сверка (`metadata.payment_id`).

## Мониторинг

```bash
docker compose -f docker-compose.scale.yml -f docker-compose.monitoring.yml up -d
ssh -L 9090:localhost:9090 -L 9093:localhost:9093 сервер      # Prometheus и Alertmanager наружу не публикуются
```

* Prometheus скрейпит **`api` и `worker`** (раньше — только api, из-за чего падение задачи воркера было незаметно).
  Метки задач воркера — `task` (`ampire_job_seconds{task="autopay"}`).
* Алерты (`deploy/prometheus/alerts.yml`) приходят в Telegram: воркер/реплика не отвечает, задача падает или давно не выполнялась,
  панель недоступна, Redis недоступен, платежи «На проверке», очередь недоставленных сообщений, не выполнялась сверка ЮKassa.
* Дополнительно **сторож внутри воркера** шлёт владельцам алерты, даже если Prometheus не настроен: зависшие задачи, Redis, панель,
  устаревшие бэкапы, очередь сообщений.
* `/metrics` — только с заголовком `Authorization: Bearer <METRICS_TOKEN>`; `/healthz`, `/readyz` и `/metrics` через публичный Caddy
  отдают 404 (Prometheus ходит напрямую по docker-сети).
* Внешний мониторинг доступности (UptimeRobot и т. п.) направляйте на главную страницу `https://ваш-домен/`.

## Проверка балансировщика (на стенде, один раз)

Caddy выполняет активные health-check только для статических upstream'ов, поэтому для `dynamic a` настроены пассивные проверки и
повтор запроса на другой реплике (`lb_try_duration 5s`). Проверьте поведение до боевой нагрузки:

```bash
docker compose -f docker-compose.scale.yml up -d --scale api=3
while true; do curl -s -o /dev/null -w "%{http_code}\n" https://ваш-домен/; sleep 0.2; done &   # во втором терминале:
docker stop $(docker compose -f docker-compose.scale.yml ps -q api | head -1)
# ожидаем: ни одного 5xx (запросы уходят на живые реплики); затем docker start … — реплика возвращается в выбор
```

## PgBouncer

При `DB_PGBOUNCER=true` бот отключает кэш prepared statements и задаёт уникальные имена подготовленных запросов
(`prepared_statement_name_func`) — это исключает ошибки `prepared statement ... already exists` в transaction-режиме.
Серверные таймауты (`statement_timeout`, `idle_in_transaction_session_timeout`) при PgBouncer задавайте на роли БД:

```sql
ALTER ROLE ampire SET statement_timeout = '30s';
ALTER ROLE ampire SET idle_in_transaction_session_timeout = '60s';
```

Проверьте на стенде перед включением: `scripts/ci_smoke.py` с `DATABASE_URL`, указывающим на PgBouncer.

## Платежи: что делать, если…

| Ситуация | Что происходит / что делать |
|---|---|
| Деньги списаны, подписка не продлена | Вебхук находит платёж по `metadata.payment_id`; иначе — воркер `payments` (раз в минуту) и суточная сверка ЮKassa → БД |
| Сумма не совпала | Платёж получает статус `needs_review`, владельцам приходит **один** алерт. **Платежи → На проверке** → «Начислить» или «Отклонить» |
| Автосписание: таймаут ЮKassa | Платёж **не отменяется**, пользователю ничего не пишется; запрос повторяется с тем же ключом идемпотентности |
| Автосписание: «нет денег» | Повторы через 1 и 3 суток; доступ сохраняется (льготный период); потом автопродление отключается |
| ЮKassa вернула 401/403 | Автопродление **не отключается** для всех: владельцам приходит алерт, попытки повторяются через час |
| Два админа нажали «Вернуть деньги» | Платёж «захватывается» (`refunding`) — второй получит отказ, дни снимутся один раз |
| После восстановления БД не хватает платежей | **Система → Сверка ЮKassa → БД**, затем подтвердите найденные в «На проверке» |

## Роли администраторов

Владельцы (`OWNER_IDS`) — всё. Остальным выдаётся одна роль (**Админка → Админы**):
`Поддержка` (пользователи, платежи на просмотр), `Биллинг` (платежи и спорные платежи, дни, статистика),
`Маркетинг` (промокоды, рефералка, рассылки, тексты), `Инфраструктура` (узлы, сквады, диагностика), `Администратор`
(всё, кроме действий владельца). Только владельцам: возвраты, управление админами, удаление пользователей, бэкап, сверка, массовый ресинк.
Начинайте с самой узкой роли.
