# Резервные копии AmpireVPN: PITR, копия вне сервера, тест восстановления

## Зачем не хватает ежедневного дампа в Telegram

Дамп раз в сутки в Telegram — это:

* **RPO до 24 часов.** После восстановления оплаты за сутки пропадут, а деньги у вас уже есть;
* **лимит ~49 МБ** на файл — с ростом базы дамп перестанет влезать;
* в дампе **ссылки доступа к VPN, email и платежи** — открытым его отправлять нельзя.

Поэтому основа теперь — **непрерывный архив WAL (PITR)** и копия **вне сервера**. Дамп в Telegram остаётся лишь
дополнительной копией «под рукой» и **отправляется только зашифрованным** (без `BACKUP_PASSWORD` бот его не шлёт и предупреждает).

## Что настроено в репозитории

| Компонент | Что делает |
|---|---|
| `docker-compose.backup.yml` | подменяет `postgres` на образ с pgBackRest, включает `archive_mode`, `archive_timeout=60` и запускает контейнер `pgbackrest` |
| `deploy/backup/pgbackrest.conf` | S3-репозиторий, шифрование `aes-256-cbc`, хранение 4 полных + 7 разностных копий |
| `deploy/backup/backup-loop.sh` | ежедневно копия (воскресенье — полная, остальные дни — разностная), метка свежести в Redis |
| `deploy/backup/restore-test.sh` | **раз в месяц** поднимает копию во временной БД, читает данные, удаляет; результат — в Telegram |
| сторож в воркере | алерт владельцам, если свежей копии нет дольше `BACKUP_MAX_AGE_H` (36 ч) или тест восстановления не выполнялся 40 дней |

RPO — около минуты (WAL уходит в S3 каждые ≤60 секунд). RTO зависит от размера базы (обычно минуты — десятки минут).

## Настройка (один раз)

1. **Хранилище.** Создайте бакет в S3-совместимом хранилище **у другого провайдера или на другой площадке**, чем сервер с ботом
   (Yandex Object Storage, Selectel, Backblaze B2, MinIO на другом сервере…). Включите версионирование/защиту от удаления, если есть.
2. **`.env`** — блок «Резервные копии»: `BACKUP_S3_ENDPOINT`, `BACKUP_S3_BUCKET`, `BACKUP_S3_KEY`, `BACKUP_S3_SECRET`,
   `BACKUP_S3_REGION`, `BACKUP_S3_URI_STYLE` и **`BACKUP_REPO_PASSPHRASE`** (`openssl rand -hex 32`).
3. **Сохраните `BACKUP_REPO_PASSPHRASE` отдельно от сервера** (менеджер паролей, сейф). Без него копии не расшифровать.
4. **Запуск:**
   ```bash
   docker compose -f docker-compose.yml -f docker-compose.backup.yml up -d --build            # один сервер
   docker compose -f docker-compose.scale.yml -f docker-compose.backup.yml up -d --build      # режим масштабирования
   ```
   Если том БД уже существовал — PostgreSQL перезапустится с включённой архивацией; данные не затрагиваются.
5. **Проверьте:**
   ```bash
   docker compose -f docker-compose.yml -f docker-compose.backup.yml logs pgbackrest | tail -30   # "check" без ошибок
   docker compose exec pgbackrest pgbackrest --stanza=ampire info                                  # список копий и архив WAL
   docker compose exec pgbackrest restore-test.sh                                                  # первый тест восстановления — сразу
   ```
6. В админке: **Система → Диагностика** — строка «Копии» должна показывать свежие «WAL/PITR» и «тест восстановления».

## Восстановление

> Перед любыми действиями остановите бота: `docker compose stop bot` (или `api worker`).

**Полное восстановление на последний момент:**
```bash
docker compose stop bot postgres pgbackrest
docker compose run --rm --no-deps -v pgdata:/var/lib/postgresql/data --entrypoint bash pgbackrest -c \
  'rm -rf /var/lib/postgresql/data/* && pgbackrest --stanza=ampire --delta restore'
docker compose up -d postgres && docker compose up -d
```

**На конкретный момент (PITR),** например за минуту до ошибочного удаления:
```bash
... pgbackrest --stanza=ampire --delta --type=time "--target=2026-11-09 14:29:00+03" --target-action=promote restore
```

### Обязательно после любого восстановления

Платежи, которые прошли в ЮKassa **после** выбранной точки восстановления, в базе отсутствуют, а деньги получены.
Сразу запустите **Админка → Система → Сверка ЮKassa → БД** (период 72 часа): бот найдёт такие платежи по `metadata`
и заведёт их в очередь **«На проверке»**; подтвердите каждый кнопкой «Начислить подписку».
Для платежей без метаданных (старые) сверка пришлёт список ID для ручного разбора.

## Тест восстановления

Копия, которую не проверяли, копией не считается. `restore-test.sh` раз в месяц:
восстанавливает последнюю копию в `/tmp`, запускает отдельный экземпляр PostgreSQL **без архивации** (чтобы не писать в боевой
репозиторий), проверяет `users`/`payments` и свежесть данных, удаляет всё и присылает результат владельцам.
Раз в квартал стоит повторить восстановление **на отдельном сервере** по инструкции выше — это проверяет и пароль шифрования, и доступ к S3.

## Альтернативы

* **Управляемый PostgreSQL** (Yandex Managed PostgreSQL, Selectel DBaaS, Timeweb и др.) — PITR и копии вне площадки уже входят.
  Тогда уберите сервис `postgres` из compose, укажите `DATABASE_URL`/`MIGRATION_DATABASE_URL` провайдера и пропустите этот документ
  (но проверьте у провайдера срок хранения WAL и сделайте тестовое восстановление).
* **WAL-G** — аналогичная схема (архив WAL + базовые копии в S3); заменяется образ `postgres` и `archive_command`.

## Дамп в Telegram (дополнительно)

* `BACKUP_TELEGRAM=true` и `BACKUP_PASSWORD` — зашифрованный дамп владельцам раз в сутки. Расшифровка: `scripts/decrypt_backup.py`.
* Не помещается в 49 МБ — бот предупредит и перестанет слать дамп; полагайтесь на PITR.
* При сбое отправки бот повторяет попытку (до 6 раз в сутки), а не «пропускает день».
