# AmpireVPN — подготовка к большому числу пользователей

> Честно: нагрузочное тестирование в этой среде провести было нельзя. Ниже — архитектура, расчёты и чек-листы,
> а не измеренные цифры. Перед рекламной кампанией прогоните реальный пилот и следите за метриками (раздел 5).

## 1. Архитектура

```
Telegram ──webhook──▶ Caddy (балансировщик, HTTPS)
                         │  least_conn + пассивные health-check + повтор на другой реплике
              ┌──────────┼──────────┐
              ▼          ▼          ▼
            api #1     api #2     api #N        ← без состояния: хендлеры бота, вебхуки ЮKassa/CryptoBot, /dl, /add, /metrics
              └──────────┬──────────┘
                         ▼
        PostgreSQL (источник истины)      Redis (FSM, блокировки, кэш, лимитер, шина событий)
                         ▲
                       worker  ← напоминания, истечение подписок, сверка платежей, рефералы, автопродление, рассылки, бэкапы, очистка
                         │
                 Remnawave API (панель)  ← закрыта кэшем, лимитом параллелизма и circuit breaker
```

Роли процесса задаются `APP_ROLE`: `all` (всё в одном, по умолчанию), `api`, `worker`.
Режим Telegram — `TELEGRAM_MODE`: `polling` (одна реплика) или `webhook` (любое число реплик `api`).

Что делает систему безопасной при нескольких копиях:

| Проблема | Решение |
|---|---|
| Две реплики меняют подписку одного пользователя | распределённая Redis-блокировка на пользователя + блокировка строки в PostgreSQL |
| Фоновая задача выполняется дважды | блокировка задачи в Redis: выполняет ровно одна реплика (дополнительные worker-ы — резерв, а не ускорение) |
| Настройки/тексты/тарифы устарели на другой реплике | Redis pub/sub + перезагрузка раз в минуту |
| Упёрлись в лимит Telegram ~30 сообщений/с | раздельные токен-бакеты в Redis для ВСЕХ реплик: рассылки (`TG_BROADCAST_RATE`, 18/с) и служебные уведомления (`TG_BG_RATE`, 8/с) — рассылка не задерживает «оплата получена» и «подписка закончилась»; рассылка идёт параллельными отправителями (`BROADCAST_CONCURRENCY`) |
| Панель Remnawave «легла» | circuit breaker (пауза 20 с после 5 ошибок), лимит параллелизма, экспоненциальные повторы синхронизации |
| Панель тормозит от частых запросов | кэш списка устройств (20 с), статистики (45 с), счётчиков (60 с) |
| Рассылка прервалась при перезапуске | курсор в БД; исполнитель берёт блокировку и продолжает с места остановки |
| Потеряли вебхук платежа | сверка статусов воркером (ЮKassa — по одному, CryptoBot — пакетно через `getInvoices`) |

## 2. Как включить режим масштабирования

1. Нужен домен с HTTPS на этот сервер и `PUBLIC_BASE_URL=https://…` (Telegram шлёт апдейты только на https).
2. В `.env` ничего менять не обязательно: роли и режим заданы в `docker-compose.scale.yml`. При желании увеличь `DB_POOL_SIZE`.
3. Останови одиночную версию: `docker compose down`.
4. Запусти: `docker compose -f docker-compose.scale.yml up -d --build --scale api=3`.
5. Проверь: `/admin → Система → Диагностика` (роль, webhook, воркеры), `curl https://bot.example.com/readyz`.
6. Масштабировать дальше: `docker compose -f docker-compose.scale.yml up -d --scale api=6`.

Данные (PostgreSQL, Redis) переиспользуются: переход с одиночного режима не требует миграции.

## 3. Размеры и настройки

**Соединения с БД.** Всего = процессы × (`DB_POOL_SIZE` + `DB_MAX_OVERFLOW`). Пример: 6 api + 1 worker, пул 8+8 → до 112 соединений;
в scale-файле у PostgreSQL `max_connections=300`. При десятках реплик ставь **PgBouncer** (режим transaction), `DB_PGBOUNCER=true`
и отдельный `MIGRATION_DATABASE_URL` на прямой адрес БД.

**Telegram.** Лимит ≈ 30 сообщений/с на бота. Фоновые отправки разделены на корзины: рассылки `TG_BROADCAST_RATE` (18/с) и служебные `TG_BG_RATE` (8/с); сумма < 30/с, остальное — запас для ответов пользователям. Параллельная отправка (по 25 получателей) даёт скорость, близкую к лимиту, а не «1 / задержка Telegram»:

| Получателей рассылки | При 20 сообщ./с |
|---|---|
| 10 000 | ≈ 8 мин |
| 100 000 | ≈ 1 ч 23 мин |
| 1 000 000 | ≈ 13 ч 53 мин |

Напоминания об окончании подписки идут тем же лимитом, поэтому один «день массовых окончаний» растягивается во времени, но ничего не теряется.
(У Telegram есть платные широковещательные рассылки до 1000 сообщ./с — в бота не включены.)

**Панель Remnawave.** Пока бот в норме, к панели идут только: создание/обновление пользователя при покупке и изменении подписки,
список устройств (кэш 20 с) и проверки рефералов (backoff по возрасту: 15 мин → 1 ч → 6 ч → 12 ч → 24 ч, основной путь — вебхук панели; нагрузка определяется числом «созревших», а не всей очередью). Параллелизм ограничен `PANEL_CONCURRENCY` (20), запросы к панели не держат соединения БД.
Если панель недоступна, пользователи видят подписку из БД, а изменения копятся и применяются автоматически.

**Redis.** Хранит FSM, блокировки, кэш и лимитеры. Потеря Redis не ломает данные: пользователи, платежи и подписки — в PostgreSQL;
пропадут только незавершённые диалоги. В compose включён AOF. Для продакшена с высокой нагрузкой — управляемый Redis/реплика.

**PostgreSQL.** Включены частичные индексы под выборки «активные подписки / ждут синхронизации / автопродление / оплаченные платежи».
Старые данные чистит воркер раз в сутки (журнал действий — 180 дн., неоплаченные платежи — 90 дн.; **оплаченные платежи не удаляются**).
Единственный primary — осознанное ограничение; для отказоустойчивости используй управляемый PostgreSQL (HA) или Patroni.

## 4. Миграции схемы

Схема управляется Alembic (`alembic/versions`). При старте процесс берёт advisory-lock в PostgreSQL и применяет `upgrade head`,
поэтому одновременный запуск нескольких реплик безопасен. БД, созданная первой версией проекта (без `alembic_version`),
автоматически приводится к актуальной схеме. Новая миграция: `alembic revision --autogenerate -m "описание"` внутри контейнера
(и обязательно закоммить файл из `alembic/versions`).

## 5. Мониторинг

Задайте `METRICS_TOKEN` — заработает `/metrics` (формат Prometheus; токен — только в заголовке `Authorization: Bearer`).
Метрики живут в процессе, который их породил, поэтому скрейпить нужно **и `api`, и `worker`** (раньше собирался только api, и
`job_errors_total`, `job_seconds`, `panel_*`, платежи из воркера были невидимы). Готовая конфигурация и алерты —
`deploy/prometheus/` и `docker-compose.monitoring.yml` (см. [`OPERATIONS.md`](OPERATIONS.md)).

Главные метрики: `ampire_tg_updates_total`, `ampire_handler_errors_total`, `ampire_payments_total{provider,status}`,
`ampire_panel_request_seconds` (гистограмма), `ampire_panel_circuit_opened_total`, `ampire_job_seconds{task}` (гистограмма),
`ampire_job_errors_total{task}`, `ampire_job_last_success_timestamp{task}`, `ampire_payments_needs_review`, `ampire_outbox_size`,
`ampire_redis_up`, `ampire_panel_circuit_open`, `ampire_sync_pending_users`, `ampire_yookassa_recon_last_run_timestamp`.
Ошибки с трассировкой — в Sentry (`SENTRY_DSN`), логи — JSON (`LOG_JSON=true`) с полем `user_id`; общий журнал ошибок всех
реплик — в админке (Система → Журнал ошибок).

## 6. Автопродление на большой когорте

Раньше один прогон обрабатывал не больше 300 пользователей раз в 10 минут (≈1 800/ч) — когорта в 10 тысяч не успевала в окно.
Теперь воркер идёт постранично, пока есть кому списывать (бюджет 4 минуты на прогон, прогон каждые 5 минут, 8 параллельных
списаний), сначала списания, потом напоминания; напоминание «за сутки» уходит в окне 24 ч → 3 ч до конца подписки.
Повторы — через 1 и 3 суток с льготным доступом; зависшее списание блокирует новое (нет двойных списаний).

## 7. Чек-лист перед запуском

- [ ] Режим `webhook` + минимум 2 реплики `api`, отдельный `worker`; `/readyz` отвечает 200 на всех репликах.
- [ ] PITR и копия вне сервера настроены ([`BACKUP.md`](BACKUP.md)), тестовое восстановление выполнено; `BACKUP_PASSWORD` задан для дампа в Telegram.
- [ ] Мониторинг и алерты подключены (api **и** worker); `TG_BROADCAST_RATE` + `TG_BG_RATE` < 30; деплой — `deploy/scripts/rolling-update.sh`.
- [ ] Ноды Remnawave рассчитаны на пиковый трафик (это отдельная от бота инфраструктура!).
- [ ] Проверены пробный период, оплата (ЮKassa и CryptoBot), апгрейд, рефералка и автопродление на тестовых аккаунтах.
- [ ] Пилот на малой аудитории (1–2 тыс.) и наблюдение за метриками 24–48 часов, затем рост.

## 8. Что не решено (и почему)

* Один primary PostgreSQL — нужен управляемый HA, это вне бота.
* Пропускная способность и география нод VPN — зона ответственности панели и серверов.
* Нагрузочный тест нужно прогнать на вашей инфраструктуре: `scripts/loadtest.py` (только на стенде!) даёт отправную точку — задержки и ошибки веб-слоя и обработки апдейтов; нагрузку на ноды VPN он не измеряет.
